# Scheduling

## Approved pipelines

1. Read the pipelines listed in the approved plan. Validate every step belongs to exactly one pipeline, ordered steps and prerequisites exist, and dependencies have no cycles. Confirm path ownership and shared resource isolation before starting parallel work. Return changes to approved design or scope to the user.
2. Count the **total approved pipelines**, independent of the current ready count. With one pipeline, the coordinator runs `go-work` sequentially in the ticket checkout. With multiple pipelines, dispatch one Standard worker and one isolated Git worktree per pipeline when its prerequisites have integrated and verified. Dispatch the only ready pipeline too. Launch as many independent ready pipelines as slots allow. Within each pipeline, keep the same worker, worktree and step order.
3. Before launching, record pipeline ID, worktree, starting SHA and launch intent under `## Progress` in the original `agent-view/checklist.md`. Record the worker/session ID as soon as available. Read those records on resume, along with actual host/worktree state. Reuse running workers. Match integrated commit SHAs to their ticket ancestor. A stale host or ambiguous launch intent must be reconciled against worktree and worker evidence before any retry. Preserve worktree changes and unfinished evidence. Never dispatch a second worker for running or integrated work.
4. Give each worker the verified ticket identity, assigned worktree, starting SHA, approval fingerprint, ordered pipeline steps, verified dependencies and original task storage paths. The worker uses evidence-only test modes and returns each step’s scoped diff, red/green or other evidence, and ordered approved commits. The coordinator owns shared progress, reports and the changelog.
5. Integrate each pipeline’s reviewed commits in dependency order. Preserve existing user changes/index. Resolve an in-scope conflict against both outcomes and rerun affected checks. If it exposes a new dependency or ownership change, stop the affected pipelines and seek revised approval. Keep worker worktrees until integration succeeds; abort an unresolved cherry-pick sequence to restore its start.
6. Record integrated evidence, then release dependents. A failed or incomplete pipeline blocks its dependents; independent pipelines can finish. Run the planned tests and review on the integrated checkout. Remove clean worktrees after verifying integration.

For explicit uncommitted delivery, execute in dependency order in the ticket checkout without touching the index or HEAD. Honor per-step approvals unless the user pre-approved all steps. Non-Git checkouts can use the same sequential route; they cannot launch Git worktrees.
