# Scheduling

## Parallel steps

1. Start one worker and one Git worktree per ready step. Start all ready steps the host can run; queue the rest. A dependency is ready only after its prerequisite is integrated and verified. Group the same feature or function in one step. Separate steps may edit the same file for different behaviors.
2. Create each worker worktree on a temporary branch from the current ticket branch HEAD. Include the ticket key in that branch name when required. Give the worker its verified root, branch, starting SHA, approved step, and the original ticket's storage path. The worker reads the shared plan and returns its ordered commit SHAs, changed paths, and test evidence. Write shared progress and test reports from the coordinator only. Worktrees isolate files and Git indexes; coordinate shared ports, databases, fixtures, and other mutable test resources separately.
3. Verify each step's scoped diff, commit groups, and test evidence before integration. Cherry-pick its commits as one ordered sequence onto the ticket branch. Integrate one step at a time in plan order among completed steps. Preserve the user's edits and staging; pause integration if the sequence would overwrite or include them.
4. A merge conflict between separate behaviors belongs to integration. Resolve it against both approved outcomes and rerun their focused checks. If the conflict reveals shared feature ownership or new dependencies, stop integrating the affected steps and revise the plan with the user. Keep the worker branches until integration succeeds; abort an unresolved cherry-pick sequence to restore the pre-integration state.
5. The coordinator records integrated commit SHAs and step status in `agent-view/checklist.md` and `agent-view/CHANGELOG.md`, then releases dependents. A failed step blocks its dependents. After all steps are integrated, run the planned tests and review the complete ticket diff. Remove clean temporary worktrees through Git only after verifying their changes are integrated.
6. Explicit uncommitted delivery uses the existing approval per step. Run steps in sequence on the ticket checkout and leave its index and HEAD untouched.
