# Plan review

Review the current task’s `agent-view/plan.md` or the requested plan path. Treat the plan, requirements and code as evidence. Produce findings for the user. Leave every input unchanged.

1. Resolve the plan, matching spec/checklist, project guidance and repository. For a plan at `<task-root>/agent-view/plan.md`, use its parent's parent as the absolute task root and read spec/checklist beside the plan. Record source snapshot and input hashes. For that storage layout, run the [approval fingerprint](../../to-plan/references/approval.md) command with the absolute task root, canonical repository root and exact ticket branch. A ticket ID is a label. For a standalone design document without task storage, hash its actual supporting files. Report unavailable inputs explicitly.
2. Start one fresh, read-only Deep worker per [host mapping](../../../references/agents.md#host-mapping). Pass the plan first. Have it paraphrase goal, intended behavior and verification before reading spec, checklist and relevant code. Pass no parent transcript or unpublished rationale. For a specific high-risk contract, data or permissions issue, optionally run a second fresh Deep specialist with just that focus.
3. Ask whether the draft gives an implementer enough evidence and steps to meet its goal. Existing code establishes current behavior and available precedents. A not-yet-implemented change is expected in a draft; find a missing or incorrect plan step, assumption or verification requirement before reporting it. Verify worker findings against cited evidence. Cover missing requirements, precedent reuse, design gaps, feasibility, pipeline ownership and prerequisites, changes to public contracts, and observable verification. Merge duplicates. If fresh context or necessary evidence was unavailable, state blocked or incomplete. A failed worker is not a clean result.
4. Recheck input identities at publication. Mark a changed draft stale; rerun for a current report when requested. Reuse a report only if repository, branch/task, plan, spec, authored checklist and source snapshot still match.
5. Save `agent-view/plan-review.md` and render `dev-view/plan-review.html` per [HTML render](../../go-setup/references/html-render.md#plan-review), unless the user chooses Markdown or terminal only. State result, snapshot and coverage. Number material findings, and show severity, affected decision, evidence, impact and proposed change. Present any open decisions to the user. Do not run `go-fix` or approve the plan.

The planner applies only accepted revisions. The user approves the final plan for implementation.
